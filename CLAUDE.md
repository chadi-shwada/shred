# ShredRGPD

Outil libre et gratuit pour exercer ses droits RGPD (effacement, accès, relance) face aux sites qui exposent des données issues de fuites. Site statique React + TypeScript + Vite, sans serveur. Langue de l'interface et des lettres : français.

## Commandes

```bash
npm install
npm run dev         # développement
npm run typecheck && npm run lint && npm test && npm run build   # à lancer avant chaque commit
npx prettier --write "src/**/*.{ts,tsx}"   # mise en forme (.prettierrc)
```

## Structure

- Types de demande RGPD : table unique `INITIAL_KINDS` dans `src/lib/letters.ts` (libellé, formulation, article), utilisée par le suivi, la relance et la plainte CNIL.
- `src/lib/` : logique pure et testée (dates, lettres, suivi, slug, `pwned.ts` pour le test de mot de passe, `breaches.ts` pour le catalogue des fuites et la reconnaissance des fuites dans un texte collé (`findBreachesInText` : nom exact, casse comprise, mot entier ; coché d'office seulement s'il est seul sur sa ligne et porté par une seule fuite), `letterLink.ts` pour pré-remplir une lettre depuis une fuite, `domain.ts` pour la recherche WHOIS/ICANN, `ics.ts` pour le rappel d'échéance, `complaint.ts` pour le récapitulatif et le dossier de plainte CNIL, `actionPlan.ts` pour le plan d'action selon les données exposées, `password.ts` pour le générateur de mot de passe : `crypto.getRandomValues`, tirage sans biais par rejet, `breachPages.ts` pour les pages par fuite, le résumé de l'accueil et le flux Atom, `vtt.ts` pour les sous-titres, `risk.ts` pour le niveau de risque indicatif d'une fuite : élevé, moyen, faible, règle affichée à côté du badge). Pas de React ni de DOM ici.
- `src/config.ts` : adresse du site (`SITE_URL`), auteur, pages du sitemap, titre et description, et `SOURCE_CODE_URL` (https://github.com/chadi-shwada/shredrgpd, dépôt public depuis le 6 octobre 2026 : liens « Code source » et mention « code ouvert » affichés ; avec null, ils sont masqués).
- `scripts/breach-logos.mjs` : appelé par `fetch-breaches.mjs`, télécharge au build les logos des fuites françaises (champ HIBP `LogoPath`) dans `public/logos/` et écrit `src/data/breach-logos.generated.json` (non versionnés). PNG, JPEG, GIF ou WebP seulement, reconnus par leur signature (jamais de SVG, qui peut contenir du code), 300 Ko au plus ; en cas d'échec, la fuite garde son médaillon. Un logo clair sur fond transparent (logo blanc, `isLightLogo` de `og-logos.mjs` : luminance moyenne > 0,5) est noté `light` dans le manifeste `{ src, light }` et posé sur un fond sombre, sur le site comme dans les images de partage ; le log du build les liste. Servis par le site : aucune requête externe pour les visiteurs. Mention « marques de leurs propriétaires, aucun lien avec ShredRGPD » (`LOGO_NOTICE`) près des logos. Testé dans `src/lib/breachLogos.test.ts`.
- `scripts/fetch-breaches.mjs` : lancé par `prebuild`, télécharge le catalogue public HIBP (`/api/v3/breaches`, métadonnées, CC BY 4.0) vers `src/data/breaches.generated.json` (non versionné). En cas d'échec, le build continue et la page Vérifier affiche « liste indisponible ». HIBP n'indique pas de pays : `scripts/french.mjs` marque une fuite comme française (`IsFrench`) si son domaine est en `.fr`, figure dans une courte liste d'entreprises françaises connues (Dailymotion, Deezer) ou si sa description cite « French » ou « France » (heuristique, testée dans `src/lib/french.test.ts`). Sans recherche, la page Vérifier n'affiche que ces fuites, hors logiciels malveillants, listes de spam et fuites fabriquées ; la recherche couvre toutes les fuites. `src/breachCatalog.ts` le charge à la demande via `import.meta.glob`.
- `src/reveal.ts` : apparition douce des blocs au défilement (lancée par `App` à chaque page) ; seuls les blocs sous l'écran sont masqués, rien si `prefers-reduced-motion` ou sans JavaScript.
- `scripts/og-logos.mjs` : lancé par `prebuild` après `fetch-breaches.mjs`, colle le logo de l'entreprise (carré arrondi blanc, sombre pour un logo clair, logo centré) à la place du médaillon dans chaque image de partage, à la position notée dans `public/og/marks.json`. Résultat dans `public/og-logo/` (non versionné), préféré par `vite.config.ts` à `public/og/`. JavaScript pur (`jpeg-js`, `pngjs`, devDependencies) ; sans logo, l'image de base reste. Testé dans `src/lib/ogLogos.test.ts`.
- `scripts/og-images.mjs` : images d'aperçu 1200×630 (JPEG) des pages de fuite dans `public/og/`, rendues avec Chromium (`playwright-core`, devDependency) à partir de la logique du site chargée par Vite. À lancer à la main (`CHROMIUM_PATH=… node scripts/og-images.mjs`) quand de nouvelles fuites françaises arrivent ; une fuite sans image garde `og.png` (`vite.config.ts` vérifie).
- `src/browser.ts` : accès au navigateur (téléchargement, presse-papiers).
- `src/useTracking.ts` : hook qui persiste le suivi dans `localStorage`.
- `src/router.ts` : routage par chemin (`/verifier`, `/que-faire`, `/lettre`, `/suivi`, `/ressources`, `/a-propos`, `/mentions-legales`, et `/fuite/<nom>` pour les pages de fuite) ; une adresse inconnue reçoit `404.html`. Les liens vers des fichiers (`/fuites.xml`, `.mp4`) ne passent pas par le routeur (`isAppLink`). Les paramètres de pré-remplissage vont dans le fragment (`/lettre#site=…`), jamais dans `?…`, pour ne pas apparaître dans les journaux de l'hébergeur. Les anciennes adresses `#/page?…` sont converties. Le générateur lit `type`, `site`, `contexte`, `fuite`, `date-fuite`, `donnees`, `autres`, `cible`, `depuis`, `premiere`, `suivi`.
- `src/data/contacts.ts` : contacts DPO indexés par le nom HIBP de la fuite, utilisés par les lettres groupées. Source (page officielle) et date de vérification obligatoires (`contacts.test.ts`). Quatre entrées (FreeMobile, BouyguesTelecom, Boulanger, FFR), relevées par l'auteur sur les pages officielles le 7 octobre 2026 : ces sites ne sont pas joignables depuis l'environnement de dev, et un résumé de moteur de recherche ne suffit pas (règle 3). Clé = nom HIBP, pas le titre (la fuite Free d'octobre 2024 est `FreeMobile`) : la vérifier sur le lien « Fiche de la fuite sur HIBP » de la page publiée. En attente : Deezer (source fournie sur zen.deezer.com, l'application Zen, et `privacy@deezer.com` trouvé ailleurs) et Cultura (adresse du formulaire OneTrust manquante).
- `localStorage` : `shred.suivi.v1` (suivi, avec contexte de la lettre et copies facultatives des lettres), `shred.plan.v1` (plan d'action coché), `shred.verifier.nouvellesFuites` (date de dernière visite pour le bandeau des nouvelles fuites françaises, écrite seulement après le bouton « Me signaler les nouvelles fuites » de la page Vérifier, effacée par « Ne plus me les signaler » : traceur demandé expressément, donc sans bandeau de consentement ; l'ancienne clé `shred.verifier.derniereVisite`, écrite d'office jusqu'au 7 octobre 2026, est effacée au chargement). Aucun cookie. Les mentions légales listent ces trois usages. Accès via `readStorage`/`writeStorage` de `src/browser.ts`.
- `src/data/sites.ts` : sites connus. Source et date de vérification obligatoires (vérifié par `sites.test.ts`). Vide pour l'instant.
- `public/videos/` : une seule vidéo muette, `shred-presentation` (45 s, 60 i/s : le principe en animation, sans démo pas à pas), avec affiche `.jpg` et sous-titres `.vtt`. Textes dans `src/data/videos.ts` (source unique : transcription affichée et `.vtt` ; alignement vérifié par `videos.test.ts`, format par `src/lib/vtt.ts`). Accueil : `ShowcaseVideo` muette, en boucle, lancée quand elle devient visible et mise en pause hors écran (rien n'est téléchargé avant), bouton pause (WCAG 2.2.2), pas de lecture automatique si `prefers-reduced-motion` ou mode économie de données, bordure en dégradé qui tourne (`@property --frame-angle`, figée si animations réduites). Ressources : la même vidéo dans `VideoPlayer` (`preload="none"`, contrôles, sans lecture automatique). Transcription repliable sous chaque vidéo. Fuites réelles (catalogue HIBP) avec les vrais logos de Free, Deezer et Bouygues Telecom (copiés depuis le build Vercel, mention « marques de leurs propriétaires » à l'image), personne fictive. Les `.mp4` sont produits hors du dépôt (animation HTML rendue image par image avec Playwright, encodage ffmpeg). Le source de l'animation n'est pas versionné : le 7 octobre 2026, « applicatif » a été ajouté sous « 0 serveur » (35,6 à 40,1 s) par retouche de l'image (Inter rendu par Chromium, position, opacité et flou mesurés image par image), seul le segment entre les images clés de 33,33 s et 41,67 s a été réencodé (mêmes réglages x264, SPS et PPS identiques), le reste est identique au bit près.
- `src/pages/`, `src/components/` : interface. En-tête (`Layout.tsx`) : pleine largeur en haut de page, puis barre détachée, arrondie et flottante dès que la page défile (`data-scrolled`, 12 px du haut par `transform` car une marge fusionnerait, marges intérieures 1,25 rem et 0,85 rem, transitions coupées si animations réduites) ; petit drapeau français décoratif à côté du logo. `ConfirmDialog` : fenêtre de confirmation (`<dialog>` modal, focus sur « Annuler », Échap annule) à la place de `window.confirm`, utilisée pour supprimer une demande ou tout le suivi. `ShredSheet`, `BinaryField`, `ScrambleText`, `DataStream`, `FooterWord`, `ShredBurst` (bandes de papier à la copie d'une lettre et quand une demande est satisfaite), `BreachMark` (repère d'une fuite : logo de l'entreprise s'il a été téléchargé au build, sinon initiale sur une teinte tirée du nom) et `Logo` sont décoratifs (`aria-hidden`, figés si `prefers-reduced-motion`).
- `src/styles/global.css` : tokens de couleur et de typographie, mode sombre inclus. Listes déroulantes (`.select`) : la liste ouverte suit le design du site dans Chrome et Edge 135+ (`appearance: base-select`), liste native en sombre ailleurs (`color-scheme`). Le site est entièrement sombre : `<html class="theme-dark">` dans `index.html` (choix de design). Les tokens clairs de `:root` restent comme base.
- Nom : « ShredRGPD » (renommé le 6 octobre 2026 : la marque de l'Union européenne SHRED.AI, n° 019221223, classe 42, couvre les logiciels en ligne). Logo : S découpé, puis « Shred » et « RGPD » en bleu (`.brand__rgpd`). Les identifiants internes gardent `shred` (clés `localStorage` `shred.*`, format d'export `shred-suivi`, noms de composants) pour ne pas casser les données ni les exports existants ; le dépôt s'appelle `chadi-shwada/shredrgpd` (renommé depuis `shred` le 6 octobre 2026 ; GitHub redirige l'ancienne adresse). Adresse : `https://shredrgpd.fr` (domaine acheté chez Hostinger le 6 octobre 2026, DNS chez Hostinger : `A @` et `CNAME www` vers les valeurs propres au projet données par Vercel ; `www.shredrgpd.fr` redirige en 308 vers `shredrgpd.fr`) ; `shred-delta.vercel.app` répond toujours. Marques vérifiées le 6 octobre 2026 sur data.inpi.fr : aucune « ShredRGPD » ; SHRED d'OrganiGram (UE n° 019018121) ne couvre que la marijuana (classes 29 à 44, ni 9, ni 42, ni 45).
- Identité : bleu `#2F4BDC` du logo (`public/logo.png`, tracé vectoriel dans `Logo.tsx` et `public/favicon.svg` ; aussi `theme-color` dans `index.html` : barre des aperçus Discord et barre du navigateur sur mobile), polices Inter et JetBrains Mono auto-hébergées via `@fontsource-variable` (OFL).
- `src/security.ts` : source unique de la CSP. `vite.config.ts` l'injecte en `<meta>`, `vercel.json` l'envoie en en-tête HTTP (avec `frame-ancestors`) ; `security.test.ts` vérifie qu'elles restent alignées.
- Pages de fuite (`src/pages/BreachPage.tsx`) : une par fuite française avec un domaine (`pageBreaches` ; les compilations sans entreprise, comme French Citizens, en sont exclues), adresse tirée du titre (`/fuite/free`, nom HIBP en cas de doublon). `vite.config.ts` lit le catalogue au build : une page HTML par fuite (`fuite/free.html`) ajoutée au sitemap, le flux Atom `fuites.xml` (lien dans chaque `<head>`, l'accueil et le pied de page) et le module virtuel `virtual:catalog-summary` (chiffres et 6 dernières fuites françaises pour l'accueil, sans charger tout le catalogue ; types dans `src/virtual.d.ts`). Sans catalogue : ni pages, ni flux, bloc de l'accueil masqué.
- `src/seo.ts` : titre, description et aperçu de chaque page (testé : une entrée par route de `PUBLIC_ROUTES`), données structurées JSON-LD de l'accueil (`WebSite` et `WebApplication` gratuite ; bloc de données, non exécuté, donc compatible avec la CSP) et `<lastmod>` des pages de fuite dans le sitemap (date d'ajout à HIBP). Le plugin `seo` de `vite.config.ts` génère une page HTML par adresse (`verifier.html`…, servies sur `/verifier` grâce à `cleanUrls` dans `vercel.json`), un `404.html` non indexé, `robots.txt` et `sitemap.xml`. `public/og.png` est l'image d'aperçu 1200×630.
- Pré-rendu : `npm run build` lance `scripts/prerender.mjs` après `vite build`. Il charge `src/prerender.tsx` avec Vite (`renderToString` de l'application, chemin fixé par `setServerLocation` du routeur, catalogue chargé avant) et écrit le contenu de chaque page dans son fichier HTML, à la place de `<div id="root"></div>`, pour les moteurs qui exécutent mal le JavaScript. `/suivi` n'est pas pré-rendu (contenu propre au navigateur). Les attributs `style` sont retirés du HTML pré-rendu : la CSP (`style-src 'self'`) les bloquerait. `main.tsx` remplace ce contenu par l'application (`createRoot`, pas d'hydratation) ; sur une page de fuite, il charge d'abord le catalogue (`loadedBreachCatalog`) pour ne pas afficher « Chargement… ». Testé dans `src/prerender.test.ts` ; vérifié dans Chromium : contenu lisible sans JavaScript, aucune erreur ni violation CSP avec.
- `.github/workflows/refresh-breaches.yml` : redéploiement quotidien (5 h 17 UTC) pour rafraîchir le catalogue HIBP, via le secret GitHub `VERCEL_DEPLOY_HOOK` (à créer par l'auteur ; sans lui, le workflow ne fait rien). Injecte aussi au build la CSP (`connect-src https://api.pwnedpasswords.com` seulement, `font-src 'self'`) et désactive l'intégration des fichiers en `data:` (`assetsInlineLimit: 0`), sinon la CSP bloque les petites polices.

## Règles non négociables

1. Aucune donnée personnelle envoyée à un serveur ou à un tiers. Pas d'analytics, pas de CDN de polices, pas de requête externe. Seule exception, validée : le test de mot de passe par k-anonymat vers `api.pwnedpasswords.com`, lancé par la personne, qui n'envoie que les 5 premiers caractères du SHA-1. L'e-mail ne passe jamais par ShredRGPD : la recherche se fait sur haveibeenpwned.com.
2. Aucune base de fuites, même partielle, même hachée côté serveur. L'outil aide à se défendre, il n'héberge rien. Le catalogue HIBP embarqué ne contient que des métadonnées publiques (nom, date, types de données), jamais de données fuitées ; attribution CC BY 4.0 affichée sur la page Vérifier.
3. Ne jamais inventer un contact de DPO ou de responsable de traitement. Laisser `contact` vide si on n'a pas de source.
4. Toute modification d'une lettre cite l'article du RGPD concerné et met à jour `src/lib/letters.test.ts`.
5. Ne jamais écrire de secret (token, clé d'API) dans le dépôt.

## Style

- Texte d'interface en français, casse de phrase, tutoiement, voix active. Pas de « veuillez », pas de « simplement ».
- Les lettres, adressées aux responsables de traitement, vouvoient.
- Les modèles de lettres sont indicatifs : ne jamais présenter l'outil comme un conseil juridique.
- Accessibilité : focus visible, `prefers-reduced-motion` respecté, contrastes AA sur le thème sombre, liens soulignés dans le texte, zones défilantes accessibles au clavier. Audit axe (WCAG 2.1 AA + bonnes pratiques) : 0 erreur sur toutes les pages.

## État du projet

Fait :
- générateur de lettres en 5 étapes, une à la fois (type, site, ce qui a fuité, toi, ta lettre ; indicateur d'étapes cliquable pour revenir, vérification avant de continuer, focus sur le titre de l'étape ; un lien pré-rempli avec un site commence à « Toi ») : effacement art. 17, accès art. 15, opposition art. 21.1/21.2/21.3 avec 17.1 c et 15.1 g, fermeture de compte art. 17.1 a/b, 7.3, 17.3 b, relance art. 12.3/12.4/77, signalement à l'hébergeur au titre de l'art. 16 du DSA ou au registrar et à Cloudflare au titre de leur politique anti-abus, illégalité fondée sur les art. 5 et 6 du RGPD), avec aide pour trouver le contact (ICANN, Cloudflare), en deux contextes : « exposition » (un site publie les données, art. 17.1 d, 17.2) et « violation » (l'entreprise a subi la fuite, art. 17.1 a/b, 34, 34.2, 33.3) ; copie, mailto, téléchargement, impression ;
- page Vérifier : choix « Que veux-tu vérifier ? » en 4 cartes (e-mail, mot de passe `#parcours=mot-de-passe`, entreprise qui a prévenu `#parcours=message`, données publiées `#parcours=publie`) ; parcours e-mail en étapes (cherche ton e-mail en 3 gestes, coche les fuites, quoi faire) et parcours « message » en 2 étapes, avec indicateur cliquable ; encadré « Des mots de passe font partie de ces fuites » qui mène au parcours mot de passe (fonctionnement du k-anonymat montré en 3 étapes, test, générateur, bons réflexes) ; collage de la page de résultats HIBP pour cocher les fuites d'un coup (texte effacé après analyse, jamais stocké ; format réel de la page HIBP non vérifié, d'où la confirmation), aide quand HIBP ne trouve rien, lien vers HIBP pour l'e-mail, recherche dans le catalogue des fuites, données exposées et conseils, lettre pré-remplie, plan d'action à cocher, lettres groupées (une par fuite choisie), lien vers la fiche HIBP, bandeau des fuites françaises ajoutées depuis la dernière visite ; test de mot de passe Pwned Passwords et générateur de mot de passe ;
- page « Que faire ? » : canaux officiels pour un message suspect (33700, Signal Spam, Phishing Initiative, SignalConso, Pharos ; fin de Bloctel le 11 août 2026) et démarches selon la donnée qui a fuité, vérifiés le 5 octobre 2026 ;
- suivi local avec échéances (1 mois, 3 si prolongé), export et import JSON, rappel `.ics`, copie facultative des lettres envoyées et dossier de plainte CNIL (récapitulatif, lettres, pièces à joindre) ;
- mentions légales (éditeur Cha4Sh, anonyme comme le permet l'article 1-1, II de la LCEN, ancien article 6, III : son identité est connue de Vercel, compte à son nom, confirmé par l'auteur le 6 octobre 2026 ; hébergeur Vercel Inc., nom et adresse seulement, le téléphone n'est pas exigé dans ce régime), aperçu de partage, sitemap ;
- accueil en 8 sections (accroche, vidéo, dernières fuites, par où commencer, Vérifier, confidentialité et principes, lettre d'exemple sur la vraie fuite Free, questions, appel final), apparitions au défilement, médaillons et badges de risque sur les fuites, fuites récentes en bande défilante et fiche d'accroche masquée sur mobile ; pages de fuite avec image d'aperçu propre ;
- accueil : section « Par où commencer ? » (4 cartes vers les parcours de Vérifier et Que faire ?), frise des étapes verticale sur mobile ; liste des fuites compacte (6 puis « Afficher plus », lien vers la fiche HIBP en icône) ; tous les types de données HIBP du catalogue traduits en français ;
- pages ressources et à propos, logo, animation d'accueil (fiche et aperçu de recherche avec de vraies fuites du catalogue HIBP : Deezer, Free, La Poste Mobile, ActMobile ; personne fictive, valeurs masquées) ;
- vidéo : une seule vidéo de présentation (principe en 45 s, sans la démo), en lecture automatique et en boucle sur l'accueil, avec contrôles sur la page Ressources ;
- accueil « Les dernières fuites en France » (vrais chiffres du catalogue), pages par fuite française, flux Atom, lien « Une erreur, une idée ? » vers l'auteur ; suivi : demande satisfaite mise en avant, relance qui garde le contexte « violation » ;
- CI GitHub Actions ; déploiement Vercel depuis `main` (`vercel.json`). Mise à jour quotidienne du catalogue en service (hebdomadaire jusqu'au 6 octobre 2026) : secret `VERCEL_DEPLOY_HOOK` créé, premier lancement manuel le 6 octobre 2026 (redéploiement de production, log `[fetch-breaches] 1039 fuites enregistrées dont 30 françaises`).
